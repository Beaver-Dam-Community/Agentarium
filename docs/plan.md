The core of this project is the **policy gateway, service-specific adapters, and behavioral consistency verification**. It structures the scope approved by the user, executes only requests bound to that scope, and links the actual transmission and target results as evidence. The endpoint catalog and E2E audit timeline are designed as a common foundation, supplemented by node eBPF and kernel events for execution evidence. Observation results lead to policy proposals → regression testing → human approval → staged deployment → re-verification, and completing this improvement cycle once is included in the MVP completion criteria. Gemini handles approval intent comparison and call path discovery as [AI-assisted features](#ai-assist). AI output is used solely to make decisions stricter or to generate warnings and candidates shown to humans; it does not grant permissions.

**Completion deliverables:** Selecting an action displays *user approval → policy decision → pre-transmission comparison → call attempt → target evidence → verification result*. It also displays rejections, retries, duplicates, missing logs, and unconfirmed results. It indicates confirmed, estimated, and unlinked kernel evidence, and retrieves proposals, tests, approvals, active versions, and rollback evidence for a policy defect. The approval screen also displays the results of approval intent comparison as warnings. Linking logs by itself is not treated as verification of authorization or proof of absence of bypasses.

## 1. Problems to Solve and Success Criteria

The questions an operator must answer are "Who permitted what?", "Following that permission, what was actually transmitted, queried, or modified?", and "To what extent were the results verified?". It addresses agents manipulated by external content, post-approval request modifications, duplicate executions resulting from retries, and logs that remain only within the execution realm.

| --- | --- | --- |

| Approval Consistency | Rejects modifications to recipients, body, exposed fields, or invocation count after approval, prior to transmission. | Difference between approval contract and normalized actual request, preflight rejection, target reception reconciliation. |

<a name="architecture"></a>

## 2. Boundaries, Roles, and Request Lifecycle

**The baseline environment is GCP (Google Cloud Platform)**, and execution, control, and verification services are based on GKE. The **execution realm** consists of Pods running the agent runtime, and a single Pod can run multiple logical sessions. It does not presuppose a 1:1 mapping between Pods and sessions or limiting the number of sessions inside a Pod. The **control realm** comprises the gateway, adapters, approvals, and secret brokering. The **observation realm** encompasses evidence collection, reconciliation, storage, and timeline, where the execution Pod has no permission to modify existing records. Target services serve as separate evidence sources. It is not claimed that Namespace separation alone enforces these boundaries.
### Distinguish Between Pod Boundaries and Logical Sessions

**A Pod is the privilege and egress boundary of an execution environment, and `session_id` is an application identifier that distinguishes tasks, approvals, policies, and records.** Within a single Pod, a trusted supervisor assigns session A and session B each to a dedicated fresh-exec worker. A worker is responsible for only one session during its lifetime and does not start user tasks before independent kernel exec observation, session binding COMMIT, and business readiness verification are complete. Kubernetes is neither aware of agent session creation and termination nor does it enforce "one session per Pod." `pod_uid` is auxiliary information identifying the source of an execution workload, and it does not replace a user's identity or individual session permissions.

| Management Unit | Responsibility | Guaranteed Scope |
| --- | --- | --- |
| Execution Pod | Least privilege for workloads, direct egress restrictions, non-retention of actual secrets, and resource limits. | Access boundary to external services and control planes. Does not automatically guarantee blocking of file and memory access between sessions inside the same Pod. |
| Logical Session | Distinguishes users, tasks, approval contracts, allowed actions, budgets, expirations, and audit events. | Policy and record separation for API requests whose session permissions have been verified through trusted request intake and mediation paths. |
| Session Origin Verification | Verifies the mapping among users, sessions, and execution principals registered by authenticated intake/execution managers in the control plane. Does not use arbitrarily client-supplied `session_id` as authorization. | Does not distinguish sessions solely by the same Pod UID or IP. If the origin is untrusted, it is not used as grounds for granting individual session permissions, and the request is held. |
| Strong Cross-Session Execution Isolation | In addition to dedicated processes, separate controls that actually block access to files, memory, and credentials of other sessions. | Not included in the claims of this design. Does not claim isolation against malicious code solely through session IDs, tokens, or folder distinctions. |

To ensure that approvals, budgets, and logs of session A are not applied to session B requests, the gateway verifies the correspondence between authenticated users, registered sessions, requests, and contracts. Expirations, revocations, and suspensions are also handled on a logical session basis. If session tokens can be read by other code from shared supervisor memory or same-UID files/identity mounts, signatures alone cannot prevent their theft or impersonation. Therefore, a shared Pod executing arbitrary code is not treated as a strongly isolated environment across different trust principals. If sensitive data in the same execution domain can be exposed to other sessions, data state is not assumed to be completely separated per session either, and disclosure restrictions across the shared workload scope are applied.

1. **Contract confirmation:** Transforms the user request into a structured contract of service, action, target, data, count, and expiration. The model draft is auxiliary, and the scope of authority is determined by the user or pre-established policies confirmed by a human. When creating a session in the console, the user inputs a task description (`task_statement`) and designates the target workload. The runtime polls for assignments via workload mTLS and receives a session token with a one-time claim code.
2. **Request intake and canonicalization:** The gateway verifies the session identity and issues an identifier. A trusted adapter canonicalization module inside the gateway creates an `ActionEnvelope` using a fixed catalog and schema. This step performs neither network transmission nor secret lookups.
3. **Policy evaluation:** The gateway determines deny / approval_required / allow based on the contract, identity, data state, and active policy (`policy_bundle_id`, `policy_epoch`). The decision is bound to the canonicalized request, adapter, target, and expiration, and recorded as an audit log. If allow, the gateway asynchronously calls the adapter registered in the catalog and returns `action_id` to the runtime.
4. **Pre-execution verification:** The execution adapter re-verifies the authenticated decision against the request actually scheduled for transmission. Approval consumption and count reservations are processed together within a DB transaction; after the attempt record is durably stored, secrets are injected and transmitted.
5. **Call and target evidence:** The adapter records the actual connection and response, and an evidence collector gathers receipts from its own receiving server or queries for target audits and states.
6. **Post-execution verification:** A verifier links the contract, decision, transmission, and target results. It displays the status on a timeline, and if a discrepancy is confirmed, requests a session-scoped hold from the control-health service to withhold subsequent high-risk requests for that session.
7. **Kernel evidence reconciliation:** Node sensors and kernel event linkers reconcile execution, connection, and selected path events against request and target evidence. If definitive correlation cannot be made across multiple sessions or shared processes in a single Pod, it is retained as workload evidence.
8. **Policy refinement:** A policy proposer suggests rationales and policy diffs. A policy deployment validator performs testing, human approval, staged rollout, active version verification, and rollbacks, and subsequent requests are evaluated against the verified new `policy_epoch`.

| Component | Primary Responsibility | Trust and Authority Boundary |
| --- | --- | --- |
| Policy Gateway | Determines who can use which service, action, target, and data scope. | Does not use agent-claimed service IDs, data classifications, or trace IDs as proof of authorization. |
| Service-Specific Adapter | Canonicalization, deterministic pre-transmission verification, enforcement of protocol, destination, secrets, and actual calls. | Does not widen allow scopes with new policies. Maximum deployed privileges apply only as an upper bound. |
| Behavioral Conformance Verification | Pre-verification conventions/libraries and post-hoc evidence reconciliation. | Pre-verification is enforced on the adapter transmission path. Post-hoc verifiers and proposal models have no authority to modify operational policies. Human-approved changes are applied by a separate deployer. |
| Independent Records and Target Evidence | Collecting audit events, monitoring omissions, providing external receipt and state evidence. | Distinguishes separate sources from adapter self-logs. Marks trust limitations in the event of node or adapter compromise. |

## 3. Endpoint Visibility and Behavioral Catalog

The policy unit is more specific than domain or IP: **service + action + target resource + environment/tenant + data scope**. Declared API and SDK operations of supported services are explicitly registered in adapters. Auto-discovered information is considered candidate data and is not used as grounds for policy allowance prior to registration and validation. Discovered information, connectivity status, and actual execution results are distinct pieces of evidence.

| Catalog Field | Design Details |
| --- | --- |
| endpoint_id / service_id / operation_id | Stable logical identifiers. Version, environment, tenant, and owner are recorded together. IP changes do not automatically create new permissions. |
| transport / route_template | HTTP method and route template or SDK operation. Fixed to prevent alteration into unauthorized raw URLs, arbitrary headers, or operations. |
| target_schema / request_schema | Resource type, namespace, recipient, allowed inputs, fields, and data types. Unknown fields affecting policy are rejected. |
| effect_type / disclosure | Read, create, update, delete, external transfer, trusted data source and classification, allowed disclosure fields. Classifications are not downgraded based solely on self-reporting by the model. |
| destination_constraints | Allowed host, port, TLS verification, address ranges, environment, redirect rules. Compares the resolved IP with the actual connection IP. |
| credential_binding / limits | Adapter, SA, secret references, least privilege upper bound, request size, count, rate. The secret value itself is not placed in the catalog. |
| canonicalization_version / schema_version / catalog_digest | The gateway canonicalization module and execution adapter use the same rules. `catalog_digest` is a hash of the registered operation and target content, and `catalog_version` is a display label. Mismatches in version or digest cause execution to be held. |
| evidence_level / evidence_source | Available level and source among connection, API acceptance, receipt confirmation, and business effect confirmation, along with the result confirmation deadline. Marks service-specific guarantee boundaries. |
| retry_policy / idempotency_support | Retryable causes, maximum attempts, idempotency key support, duplicate check methods. Does not automatically re-execute unverified side effects. |

## 4. Policy gateway and approval contract

The gateway uses the authenticated user and execution principal, the logical session registered in the control plane, and the fixed action definition. The Pod UID is used only as provenance information for the executing workload and is not interpreted as the identity or authority of an individual session. The policy decision input includes the service, action, target, data disclosure scope, state, and active policy. Rego makes the decision. The gateway passes only raw facts (envelope, verified session, approval snapshot, workload data state, control health) to OPA, and Rego evaluates `data.catalog.targets`, `data.receiver.allowed_disclosure_fields`, `data.standing_rules`, and `data.service_profiles` directly. If a required input is missing, the request is rejected with `CONTEXT_INCOMPLETE`. The adapter's pre-send check is a second line of defense.

**Embedded OPA and decision tracing:** OPA is embedded in the Go gateway process as a library (`github.com/open-policy-agent/opa/v1/rego`), not as a sidecar. The gateway and adapters read the `desired_bundle` row written by the deployer every 2 seconds, fetch the signed bundle object that the row points to from GCS, verify its signature (ES256, Cloud KMS key) with the OPA `v1/bundle` reader, load it, and record the bundle revision used for evaluation directly as `opa_bundle_revision`. Configuration-based download (`v1/sdk`) is not used, and the decision replay tool uses the same loading package. Every Rego rule has a stable `rule_id` constant (for example `standing.k8s_read.v1`, `disclosure.receiver.v1`), and the Rego result is `{verdict, reason_codes, matched_rule_ids, evaluated_rule_ids}`. `evaluated_rule_ids` contains every evaluated rule, including rules that passed, and it is the basis on which the policy proposal validator confirms that the rule targeted by a patch was actually evaluated. The gateway stores the raw Rego result (`rego_result`) separately from the rule IDs appended after Rego (`gateway_added_rule_ids`, intent escalation). Each decision stores the `matched_rule_ids` that served as its basis, so the timeline and the policy proposer can identify a faulty rule by ID. For each decision, the gateway stores a sanitized OPA input snapshot in `decision_inputs` and records `decision_input_ref` and `decision_input_digest` on the decision. The snapshot contains no secrets, raw logs, or raw content, only `content_digest`, and is retained for 30 days. This snapshot is the input to decision replay (`decision_replay`) in regression tests.

**Standing rule:** Only pre-approved low-risk rules may be auto-allowed without user approval. Rules are defined in the policy data `data.standing_rules` and go through the same approval and deployment procedure as the policy bundle. The initial rules are the three Kubernetes read operations on fixed namespaces (with size and count limits) and `model.generate` under the synthetic data profile. An auto-allowed decision records `standing_rule_id`, and the number of uses is limited by the session budget (`session_budgets`). The user approval contract (ApprovalContract) is for single-action approval only.

**Decision basis (`decision_basis`):** An allow decision has exactly one basis. It is one of user approval (`approval`), a user session standing rule (`standing_rule`), a service session profile (`service_scope`, Rego `service.scope_allow.v1`), or a probe for confirming policy activation (`activation_probe`, `probe.activation.v1`), and the corresponding ID is recorded with it. Service callers such as policy proposal, intent check, discovery, and the deployer are allowed only within the range of the server-defined profile table (allowed operations, budget, TTL), and requests outside that range are rejected with `SERVICE_SCOPE_DENIED`. A service session cannot receive user approval, and its actor is recorded as `service:<namespace>/<KSA>`.

An AI explanation of a "match" cannot add allowed authority. [Approval intent check](#ai-assist) can only escalate a request that a standing rule would allow to approval_required, or attach a warning to the approval screen.

| Decision | Execution behavior | Required records |
| --- | --- | --- |
| deny | The adapter does not start sending. | Request, `policy_bundle_id`, `policy_epoch`, `reason_codes`. Non-arrival at the target is checked together with a normal control group. |
| approval_required | Shows the contract and waits for approval. No secret injection or sending before approval. | Approval request, scope shown to the user, contract version, expiry, cancellation, intent check result. |
| allow | Forwards to the designated adapter only the request bound to the contract and decision. | decision_id, action_digest, `decision_basis` and its basis ID (one of `approval_id`, `standing_rule_id`, `service_session_id`, `activation_probe_id`), `policy_bundle_id`, `policy_epoch`, `opa_bundle_revision`, `matched_rule_ids`, `decision_input_digest`, `catalog_digest`, adapter, expiry. |

### Shared execution contract

The block below is a **conceptual summary** that shows the role of the three structures. The source of truth for fields, nullability, and enums is the [common data structures in the Shared Spec](tech-specs/COMMON.md#common-data-structures); if the two differ, follow COMMON. Retry conditions and idempotency support belong to the catalog operation, not to the approval contract.

```
ActionEnvelope = {
  schema_version, action_id, request_id, authenticated_actor, session_kind, session_id,
  workload_id?, endpoint_id, operation_id, canonical_target,
  environment, tenant, disclosure_fields, data_class, data_sources,
  content_digest?, content_ref?, bytes, limits,
  catalog_digest, catalog_version, canonicalization_version, raw_body_digest, action_digest
}
ApprovalContract = {            # for single-action user approval only (approval_kind = action)
  approval_id, action_id, revision, approval_kind, authenticated_actor, session_id,
  contract_digest, displayed_contract_digest, allowed_operation, canonical_target,
  disclosure_fields, content_digest?, max_actions, used_actions, policy_epoch,
  expires_at, contract_version, revoked_at?, revoke_reason?,
  intent_check_id?, acknowledged_findings
}
GatewayDecision = {
  decision_id, request_id, action_id, action_digest, adapter_id?,
  verdict, reason_codes, decision_basis?,
  approval_id? | standing_rule_id? | service_session_id? | activation_probe_id?,
  matched_rule_ids, evaluated_rule_ids, rego_result, gateway_added_rule_ids,
  decision_stage, decision_input_ref?, decision_input_digest?,
  policy_bundle_id, policy_epoch, opa_bundle_revision,
  catalog_digest, catalog_version, expires_at, authenticated_gateway
}
```

`pod_uid` is provenance information for the executing workload and is not a basis for session authority, so it is not included in the approval contract. The approved original content is kept in an access-restricted contract store (`content_ref`), and the adapter reads the original, recomputes the digest, and compares it.

**Digest convention:** Action, target, environment, disclosure fields, content, and constraints are normalized with the same version and then compared. Differences in JSON key order or encoding are distinguished from differences that change meaning. The action_digest is computed before credentials are inserted, and if needed the wire_body_digest of the outgoing body is recorded separately. The two values are not assumed to be equal.

Decision delivery is protected by mTLS service connections and immutable decision rows stored in the DB. The adapter does not accept decision JSON created by the client; it looks up the stored row. Approval is never granted based only on a trace ID or forwarded headers. Approval consumption and count limits are handled atomically even under concurrent requests. A one-time approval covers one logical action, and only retries of the same action specified in the contract are allowed, each with a separate attempt_id. Policy changes, contract revocation, and session disposal are also checked against the latest valid state at the execution adapter. If the valid state cannot be confirmed, sending is held.

The user is shown the service, action, target, disclosure fields, count, and expiry in readable form. An approval that presents only a body hash is not treated as sufficient user consent. Complete semantic verification of free-form intent is not guaranteed, and the initial scope is limited to contracts that can be expressed with a schema. The approval intent check only supplements this gap with warnings and does not widen the scope of guarantees.

**Flow after approval is pending:** The console shows pending approval requests to the session owner, then fetches and displays the server-rendered display contract and `displayed_contract_digest`. If there are intent check warnings, the user must acknowledge each item before approving. When the user approves, the runtime or console requests a re-decision of the same action. The re-decision keeps the same `action_id` and `action_digest` and issues a new `decision_id` and a new 10-second TTL. The agent cannot create approvals or provide the summary on the approval screen; it can only request approval by `action_id`. API names and fields follow the [Shared Spec](tech-specs/COMMON.md).

**Policy changes and existing approvals:** An approval records the `policy_epoch` at the time of approval. When a new epoch becomes active, a patch that narrows the disclosure scope changes unused approvals whose `disclosure_fields` are not a subset of the new allowed set to `revoked(reason=policy_changed)`. Other patches are re-decided at the next reservation.

<a name="adapters"></a>

## 5. Per-service adapters · Enforcement of actual sending

An adapter is an execution boundary that understands the API semantics of a service. The gateway's internal normalization module and the execution adapter share the same version of the schema and normalization convention. Where possible, execution adapters separate the Pod, ServiceAccount, secret, and egress permissions per service. Normal read credentials must not be able to execute send or modify actions.

| Stage | Verification and enforcement | Failure handling |
| --- | --- | --- |
| Decision authentication | Gateway principal, decision_id, request_id, adapter_id, expiry, active version. Checks for approval reuse, revocation, and disposed sessions. | Deny or re-decide. |
| Pre-send match | Compares the operation, target, environment, fields, content, and size of the actually generated request against the contract/decision. | Record the difference and refuse to send. Not replaced by a mere after-the-fact warning. |
| Destination verification | Fixed host and port, DNS result versus actual connected IP, TLS host/certificate verification. Blocks arbitrary proxies, raw URLs, and header injection. | Reject addresses outside the allowed range and unknown destinations. |
| redirect / retry | In the initial MVP, automatic redirects are disabled. If needed, each hop is re-verified and re-decided. SDK automatic retries are turned off or wrapped with explicit attempt records. | Unobserved additional calls are not allowed. |
| Execution preparation record | The dispatch coordinator durably stores the approval count reservation + preflight pass + attempt_planned. Checks health status and holds for the required recording and node sensor paths. The gateway does not reserve. | If recording is impossible, the health decision has expired, or a hold covers the scope, new risky sends are held. A failure before permit claim rolls back the reservation. |
| Secret injection and call | Injects the secret into the minimum necessary call via a fixed credential binding. Not returned to the execution Pod, ordinary responses, or audit events. | Distinguish secret and permission failures from policy denials. |
| Send and response record | Per attempt: actual connected target, send stage, response code, provider_request_id, latency. The adapter transport recorder records local/peer addresses, ports, and netns as an AdapterObservation for use in kernel connection matching. The MVP uses a new connection for each attempt and disables keep-alive. Distinguishes timeout, cancellation, partial send, and stream interruption. | Absence of a response is not confirmed as non-execution. A connection failure before the first byte is failed; no response after the request header send has started is unknown. |
| Response handling | Only the required data is sanitized and stored as the action result, and the runtime receives it through the result query API. Provenance and data class update the session/workload-level high-water mark (`workload_data_state`), which is reflected in subsequent data disclosure decisions. | Commands or policy-change wording in external responses are untrusted data. |

**Side effects and retries:** For targets that support idempotency_key, the same key is used for the same logical action. If not supported, automatic resend after an unknown response is prohibited by default, and checking the target state or re-approval is required. The document does not claim atomic exactly-once between local storage and remote execution. A crash or partial send after the approval reservation is left in the unknown state for after-the-fact reconciliation.

## 6. Action alignment verification · Result states

<a id="before-execution-the-allowed-contract-and-the-request-just-before-sending-ref"></a>

### Before execution: the allowed contract and the request just before sending

Pre-verification is enforced as a deterministic function on the adapter's send path. It compares the service, action, target, disclosure fields, content digest, size, count, and validity state of the contract, the gateway decision, and the actually generated request. Version mismatches, unknown fields, and changed conditions lead to denial or re-approval.

### After execution: adapter sends and the target's observed results

Post-verification compares send attempts against target receipts, audits, and states from a separate source. A self-hosted receiving server computes the digest of the arriving content directly and counts duplicates. A result is confirmed only when it can be deterministically linked to the corresponding action, attempt, and target response ID. Requests are not arbitrarily linked based only on the same time window or the same IP. Separately from the execution states below, `alignment` (aligned, mismatch, unknown, insufficient_evidence, observation_gap) and the evidence level are shown, and the source of truth for each enum is the [Shared Spec](tech-specs/COMMON.md).

| State | Meaning | Operational handling |
| --- | --- | --- |
| denied / approval_pending | Policy denial or awaiting approval. No call is allowed. | If a target call record appears, investigate bypass or mismatch. |
| preflight_rejected | There was an allow decision, but the contract comparison just before sending failed. | Block the send, show the difference, and obtain a new approval if needed. |
| attempt_planned / dispatched | Call preparation recorded / sending has started. | Not shown as completed or as arrived at the target. |
| accepted | Acceptance by the target API or a successful response has been confirmed. | Follow-up confirmation depending on the per-service evidence level. HTTP 200 by itself does not confirm the business effect. |
| effect_verified | Receipt or business effect has been confirmed for the approved target, content, and count. | Show the evidence source and the confirmation time and version. |
| effect_mismatch | Evidence confirms a different target, content, or scope, or a duplicate effect. | The verifier requests a session-scope hold and creates an issue for investigation. Data already sent cannot be recalled. |
| failed / unknown | Explicit evidence of failure / insufficient evidence of the result or linkage. | Timeouts and missing logs are not concluded to be failed. The state may remain unknown even after the confirmation deadline. |

The request timeline does not overwrite earlier facts with a single last state. It preserves multiple attempts and late target evidence and updates the derived state. When an operator resolves unknown with attached evidence, it is recorded as an `unknown_resolved` audit event, and the existing unknown fact is not erased. If the status query itself is an API call, a separate controlling principal, read-only permissions, a request_id, and the link to the original action are recorded.

**Retention and Writing:** Risky calls are initiated only after confirming contract, decision, preflight comparison, and attempt preparation in durable storage outside the execution Pod. Adapters and validators record to a persistent outbox with event_id, and an external collector deduplicates and acks them. Collector delay tolerance, outbox upper limits, and health determination TTLs are fixed prior to testing. If a COMMIT to an independent DB cannot be made, new risky transmissions are immediately held. External export delays are marked as `degraded`, and transitioned to hold if the delay exceeds the limit. Unknown requests are not automatically re-executed solely upon failure recovery.

**Audit and APM:** Approval, decision, attempt, and verification audit events are stored in their entirety. Performance traces may be sampled separately, but the absence of a sampled trace must not be confused with a missing audit event. Even if the trace system and audit storage use the same product, retention, sampling, and write permissions are kept distinct.

**Independence:** The recording entity is granted append-only permissions, with delete and existing modification permissions removed. Evidence must be queryable even after the execution Pod is deleted. Retention periods, storage IAM, change auditing, and external checkpoints are tested. It is not claimed that cases where adapters or hosts are compromised to leave false records can be resolved by exhaustive logs alone.

**Data Minimization:** Authorization, actual API keys, session tokens, environment variables, and full raw text are not collected. Destination identifiers are also retained as secure references depending on sensitivity, and approval details are queried from an access-restricted contract store. A digest is not a guarantee of anonymity, and low-entropy personal information requires separate protection.

### GCP Baseline Deployment

Execution, control, and verification services and test receiving servers are deployed to GKE on GCP. ### Namespaces and node pools are also execution prerequisites for the MVP

**Implemented with manually managed node pools in GKE Standard.** The cluster is created with Dataplane V2 (`ADVANCED_DATAPATH`), and `GKE_METADATA` mode is applied to all node pools. These two values are fixed decisions made at cluster creation time. Host sensor permissions, kernel, and runtime compatibility are measured empirically beforehand. Autopilot and node auto-provisioning are not used within this scope. Installation values such as node image (`COS_CONTAINERD`), private nodes, release channel, IPv4-only, and machine type are pinned in `deploy/gcp/environment.lock.json` (schema owned by TASK-16). Configure exec-pool and control-pool so that nodes are not recreated without notice due to auto-upgrade or auto-repair, with the configurable scope verified by TASK-01 against official documentation. Nodes are created with an initial taint `agentarium.io/observe-not-ready=true:NoSchedule`, and a trusted controller removes this taint only on nodes that pass the Q0 probe. Planned maintenance is operated manually in the sequence of cordon → hold → spool/ack verification → drain. A namespace is a unit of resource, RBAC, and policy management, while a node pool is a unit to reduce host sharing between execution code and control services. Neither is created on a per-session basis.

GKE-managed components and node sensors are managed under a separate exception list, without assuming that "only unprivileged Pods exist on execution nodes."

- **Placement enforcement:** Use per-pool taints/tolerations together with protected nodeSelectors. ### 8.1 Node eBPF and kernel event correlation: MVP required

Beyond the requests reported by the policy gateway and adapters, there is an evidence channel that observes actual processes and selected OS behavior. The candidate node sensor implementation is Tetragon. The host sensor is not placed as a sidecar inside the execution Pod; it is deployed as a DaemonSet on the observed nodes. The following table is not a list of automatic product guarantees but **the list of events that this MVP verifies through installation, hooks, and the ground-truth harness**.

| Minimum event | Completion evidence |
| --- | --- |
| Process execution, exit, and lineage | exec/exit with stable execution identifiers, parent relationships, and workload provenance. Reproduce an unexpected child execution of a test tool. |
| Selected network connections | Direct egress attempts from the execution Pod and the adapter's target connections. Includes the internal gateway/adapter segment as well. Do not use as-is a default example that records only external connections. Distinguish TCP connection attempts from established connections, and state the range of attempts, successes, and failures/return values that the hook sees. Do not claim to observe UDP DNS with TCP hooks. |
| Access to selected protected paths | Read/write attempts on team-owned test protected files and their possible outcomes. Distinguish opens that passed the permission check from denied attempts using separate hooks. Pin the paths, hooks, and versions, and do not claim to observe all file/system calls. |
| Sensor and control status | Sensor/node heartbeat, hook attachment, active rule hash, per-node coverage, and known loss/collection delay. The baseline verifier compares the approved baselines of policy, catalog, adapters, and sensors against the actual active values, and also compares the Admission, RBAC, NetworkPolicy, and node pool configuration baselines via periodic probes, emitting `control_drift_detected`. |

**Platform and sensor onboarding verification:** Record the GKE mode and version, node image, kernel, BTF/eBPF, required hooks and permissions, sensor version and configuration, and Sandbox observation scope, and reproduce the ground-truth events for the three behavior types above. A successful installation alone does not pass onboarding verification. Test each required node/runtime combination on which execution and adapters are deployed.

**Execution start guarantee (`startup_guard_gate`):** The start guarantee before the first code execution is an independent gate separate from kernel observation. This gate consists of start permit consumption, the runtime guard, and wrapping of the native start, and it is enabled only on node/runtime combinations that passed Q0. The [Shared Spec](tech-specs/COMMON.md#execution-start-guarantee-contract) separates filter preparation at the create stage from enforcement immediately before containerd `task.Start` (the NRI `StartContainer` response). Implement the sequence: consume the permit bound to node/boot/container/restart/image/profile → record the start intent in the independent DB → fsync the local journal → final check → return allow (nil) → containerd `task.Start`. The guard does not call start directly. The fail-open conditions of the NRI plugin path, the range of containerd settings that GKE supports, and whether the setup persists after node re-creation or upgrade are handled as confirmed facts in COMMON and as required Q0 verification items. If an exec is observed without a consumed permit, record `start_guard_bypass_detected` and hold the affected workload. Successful consumption is not evidence of an actual start; a lost response or crash is handled by state reconciliation and unknown/hold. Planned reloads are ordered with a local lock/generation fence, but losslessness is not guaranteed for unplanned sensor failures after the last check. If Q0 fails, record the combination as `startup_capture=unsupported` and hold deployment only for the short Pod profiles that need the guard. Failure of this gate does not block installation, testing, or completion judgment of other features, including kernel observation and policy improvement. Implementation and functional verification are planned.

**Lifecycle and loss of short Pods (MVP required):** The MVP-required scope for short Pods is filter preparation at the create stage, runtime/API lifecycle recording, ObservationGap recording, and 30-day retention. On combinations where `startup_guard_gate` is enabled, before the first code execution of an observed container the node runtime bridge confirms the sensor/hooks, the current generation, the Pod/container filter mapping, the exporter/WAL, the audit DB, and the lifecycle preparation COMMIT, and consumes the start permit once. On combinations with `startup_capture=unsupported`, short Pods are reported in "observable scope and gap reporting" mode, without claiming that observation before the first code execution is guaranteed. In either case, observation readiness is not judged from Pod Ready or heartbeat alone. Bootstrap exceptions are limited to approved sensors, recorders, and the like. Raw runtime/API lifecycle facts, UID/boot/container intervals, and deletion tombstones are retained for 30 days together with the related kernel originals, and watch history expiry and late metadata are recorded as gaps/correlation revisions. Distinguish the exporter WAL fsync from the independent DB COMMIT ack, and do not delete unacked records. Sequence ranges that cannot be recovered are sent as `sequence_range_abandoned` and kept as ObservationGap. Node drain is handled in the order cordon → hold → spool/ack confirmation → drain, and a forced node loss is treated as an unrecoverable gap/unknown after the last ack. [Shared Spec](tech-specs/COMMON.md#short-lived-pod-start-lifecycle-and-loss-contract), [Sensor](tech-specs/TASK-09-node-sensor.md), [Correlation/health](tech-specs/TASK-10-correlation-health.md), [Tests](tech-specs/TASK-13-regression-harness.md).

**Kernel event correlation rules:** Sensor events preserve source_event_id, node identifier/boot, time, process execution identifier/start time, parent, container_id, pod_uid, namespace, sensor/rule version, and, where available, socket/netns information. cgroup correlation uses the values that the lifecycle recorder recorded at create time. The adapter transport recorder inside the adapter process records, for each attempt, the local/peer addresses and ports, `netns_inode`, `pod_uid`, and send time as an AdapterObservation. A kernel connect/state event is stored as a **confirmed correlation** only when its `(netns_inode, 4-tuple, pod_uid, time interval)` uniquely matches one AdapterObservation; the tuple normalization rules for Service address translation are measured and fixed in Q0. Consider PID reuse, Pod re-creation, shared connections, and HTTP multiplexing, and store **confirmed correlation / workload-scope estimate / correlation unknown** together with the evidence, method, and version. Do not confirm a correlation from an ID written by the agent or from time or IP proximity alone.

**Multiple sessions in a shared Pod:** A dedicated worker per session is the default, and actor sessions are linked through a SessionProcessBinding based on trusted registration, a node witness, and a durable kernel exec. The source of truth is the [COMMON worker contract](tech-specs/COMMON.md#session-dedicated-worker-contract). The kernel does not automatically know the application session_id. If events from a shared supervisor/adapter or events missing parent relationships cannot be linked to a specific session, they are kept as Pod/process-scope evidence. When the sessions affected by a direct bypass or sensor failure cannot be narrowed down, new risky requests of that shared workload are held according to fixed rules. Kernel information is not used to judge HTTPS bodies, public fields, or user intent; that comparison is performed by the adapter and target evidence.

**Sensor protection and failure:** Agents, Gemini, and the proposer are not given the sensor control socket, host mounts, or permission to modify TracingPolicy. Raw arguments/environment variables are exported after minimal collection and redaction. Health TTL expiry, missing hooks, and loss on a required sensor are marked as observation gaps, and new risky executions of the affected workloads are held. Release requires re-confirming the active policy, hooks, and ground-truth probes after reconnection, and the system does not silently downgrade to a log-only profile. The truthfulness of the sensor is not guaranteed after a compromise of the same node/kernel.

**Hold model:** A hold is a durable record with a scope (global, node, workload, target, session) and a reason, and each reason is released only by its owning component. Other components can only request a hold, and the control-health service decides. Temporary failures with a clear cause (export delay, DB restart, temporary probe failure, etc.) are released automatically after the probe passes, and an audit event is recorded. Security reasons (drift, bypass, sensor tampering, alignment mismatch) are released only with operator approval. A hold during policy activation is also expressed in the same model with the `policy_activation` reason. The source of truth for the list of reasons is the [Shared Spec](tech-specs/COMMON.md#enum-definitions).

**Kernel/policy event correlation fields:** Kernel originals preserve sensor_id, source_event_id, rule_hash, and workload/process provenance, and action_id/attempt_id are attached only when they can be confirmed. Estimated relationships are recorded separately with correlation_id, confidence level, and evidence. Policy change records link proposal_id, issue_id, evidence_ids, candidate_digest, run_id, fixture_set_digest, change_id, approval_digest, policy_bundle_id, artifact_digest, policy_epoch, deployment target/actor, activation confirmation, and rollback target. Unknown is not filled with an arbitrary session ID.

### 8.2 Policy proposal, improvement, and deployment: MVP required

**The minimum goal is one improvement of one defect and a rollback test.** For the two initial tasks, a least-privilege draft is built from normal records, and rule changes are proposed for bypass, mismatch, over-permissive, observation-gap, and intent-mismatch cases. For every patch kind, the model proposes only builder parameters, descriptions, and evidence links; a deterministic builder produces the patch and the diff. The least-privilege draft (`policy.draft.create`) is also produced by a builder that computes the minimal set from the observed normal allowed set. Gemini may generate explanations and a structured diff draft from sanitized evidence, but the operator-reviewed policy and deterministic validation decide the scope of application. The proposal model's raw output is never executed as a deployment command. The improvement flow starts when an operator starts a proposal from an issue produced by the validator (mismatch, unknown, gap, intent mismatch).

| Stage | Policy deployment pass condition |
| --- | --- |
| 1. Evidence and proposal | Record issue_id and evidence_ids, the defective rule's `matched_rule_ids` (the rule targeted by the patch must be in the evidence decision's `evaluated_rule_ids` and must match the patch kind mapping table in COMMON), the base bundle digest (`base_bundle_digest`), the policy diff, resolved cases, expected normal impact, and the test list. Run the deterministic permission widening check (`permission_widening`) as a preview and attach the result to the proposal. Events and external content are analysis data and are not treated as instructions. |
| 2. Validation and regression tests | Only the allowed policy schema and change resources are allowed. The first step, `decision_replay`, re-evaluates stored decision input snapshots (last 7 days, inputs decided with the baseline bundle, at most 5000) with the baseline and candidate bundles on an embedded OPA of the same version as the gateway, and produces the list of requests whose decision changed and the differences in evidence rules. This result is produced before the E2E tests and serves as the normal-impact evidence in the report and the approval screen, but the replay result alone does not decide release eligibility. The required fixture set per scope is pinned in the server's fixture registry, and the model can only add tests to it. Normal lookups, transfer tasks, failure cases, and sensor/recording outages are replayed against baseline and candidate separately, with the same `fixture_set_digest`, in a regression test environment in a separate GCP project. Holdout cases not used in the proposal run only against the final candidate, and the report given to the model contains holdout results only as aggregates. Per-case 2×2 results, the number of cases whose result changed, blocks, normal successes, losses, and cost are compared, and the gate applies only to the candidate run. |
| 3. Human approval | Approve the exact diff, artifact hashes, test results, decision replay results, scope of application, normal impact, and rollback conditions. Registering a policy change requires the `run_id` of the final regression run including holdout (`run_kind = candidate_final`). The permission widening check result (`permission_widening`) is stored in the change record, and if there are widened items, the approval screen highlights them and requires per-item confirmation (`PERMISSION_WIDENING_ACK_REQUIRED`). This check holds only within the typed patch scope and does not use formal analysis tools. User action approval is distinct from operational policy change approval. A diff change after approval requires retesting and re-approval. |
| 4. Limited deployment | "Limited deployment" here is not a canary. A deployment identity with restricted permissions applies the immutable bundle only to registered targets, holds new dispatches during activation (`policy_activation` hold), and then switches `policy_epoch` atomically. During this hold, ordinary requests are not executed. Schema, permission ceiling, and approval hash are checked. Out-of-scope RBAC/IAM, Namespace, and node/sensor bootstrap changes are rejected by the MVP deployment API. |
| 5. Activation check and revalidation | The activation order is: create the `policy_activation` hold → the deployer updates `desired_bundle` → all expected replicas (Deployment `status.replicas`) report the `artifact_digest` loaded via lease (ack timeout 120 seconds) → `policy_epoch` CAS → activation probe → release the hold or roll back. Sensor rules are confirmed by per-node `sensor_generation` acks. Mixed or unconfirmed states hold the affected executions. Existing approvals are re-evaluated using the `policy_epoch` at approval time and the per-patch-kind invalidation rules. Only activation probe actions registered by the deployment identity run during the hold, to confirm the normal and forbidden effects. |
| 6. Rollback and closure | If the criteria are not met, hold new risky executions, then restore the approved previous compatible bundle, and recheck the active values and the normal/forbidden probes. Before and after evidence and deployment/rollback records are retained. Rollback does not undo remote effects that have already occurred. |

Initial change targets are limited to **gateway policy data (disclosed fields, targets, standing rules), approved catalog/adapter constraints, and registered sensor rules**. The case to improve is fixed as [the demonstration case in the Shared Spec](tech-specs/COMMON.md#one-demonstration-to-show-in-the-evaluation). The initial policy intentionally contains a defect that allows even the synthetic email field, and the report states that this case was planted in advance for the demonstration. The expected result is that a request including email is gateway `allow` in baseline (defect reproduced) and `deny` (`DISCLOSURE_SCOPE_DENIED`) in candidate, and a request containing only the summary succeeds in both. The warning from approval intent comparison is the starting evidence for this improvement. Sensor rule changes can be proposed only as an operator-authored patch (`operator_patch` in the proposal start request), and the model cannot propose sensor rules. Because sensor rule changes are high-privilege operations, they require a designated scope, human approval, and per-node application confirmation. Execution holds under fixed response rules can be automated, but the model must not be able to automatically widen the allowed scope or cluster permissions.

<a name="ai-assist"></a>

### 8.3 AI-assisted features: approval intent check and call path discovery

Besides policy proposals, Gemini handles two assistive features. Neither feature replaces deterministic controls, and the source of truth for the contract is [the Google technology usage design in the Shared Spec](tech-specs/COMMON.md#google-technology-usage-design). No new Task ID is created; the features are reflected in the deliverables and completion criteria of TASK-02, 03, 04, 05, 12, and 13.

**One-way principle:** AI output is used only to make a decision stricter (allow → approval_required) or to produce warnings, annotations, and candidates shown to humans. AI output cannot create an allow or lower a deny or approval_required, and it cannot create confirmed states such as catalog permission, confirmed links, or effect_verified. If an AI call fails or times out, the feature's status is recorded as `not_run` and the deterministic decision is used as is. Every AI call goes through the model adapter and the `model.generate` control path. "Zero cases in which AI output created an allow" (`ai_created_allow_count = 0`) is a release invariant of the regression tests.

**Approval intent check (intent check):** As stated in chapter 4, full semantic verification of free-form intent is not guaranteed. The intent check is a feature that supplements this gap with warnings and does not claim a guarantee.

| Item | Design |
| --- | --- |
| Input | The `task_statement` entered by the user at session creation and stored by the server, the structured display contract rendered by the server (target, disclosed fields, count, expiry, synthetic data content preview), and the catalog operation description. Text written by the agent is not included, and external text inside the input is marked as data, not instructions. |
| Output | Structured output returns `overall` (consistent, divergent, unclear) and a list of findings (field_extra, recipient_mismatch, count_mismatch, scope_broader, unclear), and the server re-validates the schema. If validation fails, `intent_check_status = not_run`. |
| Effect | divergent and unclear are shown as warnings on the approval screen, and the user must confirm each item before approving (`INTENT_ACK_REQUIRED`). When an operation marked in the catalog as subject to intent check is auto-allowed by a standing rule and the result is divergent, the decision is escalated to approval_required (`INTENT_DIVERGENCE_ESCALATED`). The initial time limit is 3 seconds and will be fixed by Q0 measurement. consistent adds no permission. A divergent result can create an `intent_divergence` issue, and this issue becomes an input to the policy improvement flow in 8.2. |
| Ownership | The intent checker, including decision escalation, belongs to TASK-04, and model calls go through the gateway with a service session. The model adapter's `intent_check` profile belongs to TASK-05, the approval screen warnings and confirmation records to TASK-03, and the fixtures and metrics to TASK-13. The event is `intent_checked`. |

**Call path discovery (discovery):** Produces the input that fills the visibility denominator in chapter 3. The methodology cites [REA](https://rea.tools/) only as reference material, and this revision did not verify that tool's features.

| Item | Design |
| --- | --- |
| Targets | Version-pinned libraries used by the Python runtime (ADK, google-genai, google-auth, etc.), dependencies such as the standard `net/http` and `golang.org/x/oauth2` used by Go services, and team-owned tools. Only open-source, license-permitted targets are covered; internals of external SaaS and proprietary binaries are excluded. |
| Method | In static analysis, Gemini queries a pinned source snapshot and call relationships through read tools and produces candidates for network, file, and process call sites. In dynamic observation, fixed scenarios are run with controls on/off in the analysis environment of the regression test project, and kernel sensor traces are compared with adapter records. Finally, Gemini classifies the two results as "observed but not in the static list", "static candidate but not observed", or "match". This classification is an annotation attached to candidates, not a confirmed state. |
| Promotion | AI output alone cannot register anything in the catalog or allow it. A candidate is promoted to a catalog operation registration (allow) or to a forbidden fixture or SDK configuration verification item (deny or disable) only after it is reproduced in a dynamic trace and reviewed by a human. The events are `discovery_candidate_recorded` and `discovery_candidate_promoted`. |
| Location and ownership | The analyzer runs outside the execution area (`agent-observe` or the regression test project). TASK-02 handles candidate storage and the promotion procedure, and the TASK-13 harness handles dynamic execution. |

**Completion criteria:** Implement both features and report the results measured with the fixtures in chapter 9. Even if the measured results are poor or a feature fails, the completion decision for deterministic controls is not weakened.

## 9. MVP Tasks · Verification · Metrics

**Query task:** Query and summarize Pods, events, and limited logs in the test namespace. **Transmission task:** Approve and transmit a summary generated from fake sample logs to an in-house receiving server under a structured contract. Model calls for the agent-execution demo are also included in the same control path. The initial functional verification is performed with a deterministic request harness, and subsequently repeated with an actual agent runtime built with Google ADK (Python). The model extension point in ADK was confirmed from source ([`BaseLlm.generate_content_async`](https://github.com/google/adk-python/blob/main/src/google/adk/models/base_llm.py) is an abstract method and `LlmAgent.model` is `Union[str, BaseLlm]`). Re-verify against the pinned version. Agent tools wrap only `submit_action`, `poll_action`, and `request_approval(action_id)`, and the agent's model calls are also routed to `model.generate` on the gateway.

| Test | Pass Evidence |
| --- | --- |
| Normal query · approved transmission | Approvals, decisions, preflight, individual calls, and target results are linked, and the task succeeds. |
| Prohibited actions/targets of allowed services | Rejects modifications to the same service, different namespaces, different recipients, and environment requests. Normal queries succeed. |
| Post-approval request mutation | Rejects changes to recipients, public fields, body, size, or catalog version prior to transmission. Aggregated by mutation type. |
| Logical session separation on shared Pods | Generates session A and B requests on the same Pod and verifies that A's approvals, budget, responses, and timeline are not incorrectly applied to B. Arbitrary session_id changes are rejected at the trusted ingestion path. Not construed as an OS isolation test to prevent session credential theft within the same execution environment. |
| Approval expiration · revocation · concurrent reuse | Does not exceed the allowed number of logical actions. Verifies atomic consumption, policy changes, and discarded sessions. |
| Retries · timeouts · crashes | Separates attempts, supports idempotency, and reconciles duplicates. Disallows automatic retransmission of unverified results; updates state via late receipt. |
| Destination · TLS · redirect | Rejects different host/IP, arbitrary proxies, certificate failures, and automatic redirects. Normal destinations succeed. |
| Log loss · delay · duplication · reordering | Displays gaps and delays by source; deduplicates by event_id. If an independent DB COMMIT is impossible, new risky transmissions are held; external export delays are marked degraded, and held if the limit is exceeded. |
| False completion · unconfirmed target | effect_verified is not attained solely by agent completion statements or HTTP responses. Insufficient evidence is marked unknown. |
| Direct bypass · secret probing | Contrasts direct destination, DNS, and metadata probing from the execution Pod against normal gateway calls. Separately reports whether actual secrets were exposed. |
| Pod deletion · record tampering attempt | The entire timeline can be viewed from outside the execution domain. Denies permission to modify or delete existing records. |

| Additional Required Tests | Pass Evidence |
| --- | --- |

### Measurement Denominators

| Metric | Definition |
| --- | --- |
| Action coverage | Number of actions among the required task list with defined and verified catalogs, adapters, policies, and evidence levels / total number of required actions. Separately indicates unsupported actions and the scope identified through call path discovery procedures. |
| E2E evidence completeness | Number of requests with all events required for the corresponding execution state correlated / total number of test requests. Expected events per state are based on the [Shared Spec's event_type registry](tech-specs/COMMON.md#event_type-registry). |
| Effect verification scope | Number of verified target effects / number of actually invoked actions. Separately tallies API acceptance only, mismatches, and unknown. |
| Prohibited block rate · normal success rate | Number of prohibited cases where zero effect is independently verified / number of prohibited cases; number of normal requests terminating in effect_verified or accepted as expected / number of normal requests. The two ratios use separate denominators. |
| Mutation blocking · reuse · duplication | Number of blocks prior to transmission / number of mutation attempts, number of executions exceeding approval scope, number of target duplicates per original action. |
| Normal task · operational cost | Number of successful query/transmission tasks / number of repetitions (separately for controlled runs and control-off baseline), policy/adapter/verification latency p50/p95 (p95 is measured with 100 or more repetitions of the same normal request under `run_kind = measurement`), approval counts, audit storage latency and backlog, model tokens, call counts, and call latency. Monetary amounts are calculated only when usage and applicable unit rates are confirmed. |
| Health · correlation accuracy | Number of detected injected losses/faults / number of injections, miscorrelation rate (number of miscorrelations / number of confirmed correlations), correlation recall (number of correct confirmed correlations / number of ground truth relationships), time to hold, and unobserved intervals. |
| Kernel event observation/correlation | Number of observed ground truth events by type, node, and runtime / number of injected ground truth events, miscorrelation rate and correlation recall (definitions as above), confirmed/inferred/unknown proportions, loss metrics, and sensor CPU/memory. Does not silently remove unsupported from the denominator. |
| Short-lived Pod observation · retention | Separately tallies expected event observation rate, original Pod UID attribution rate, session correlation rate, and post-deletion external query rate by target/measured process and Pod lifespan. Includes first-code rejection, gap/hold delay, and node-loss unknown. |
| Policy refinement effect · deployment | Case-by-case 2×2 results and number of outcome-changed cases on the same `fixture_set_digest`, number of replays and number of changed decisions in decision replay, number of privilege escalation items, blocked/normal success, latency, loss, number of components matching expected bundle / number of deployment targets, elapsed time for approval, deployment, and rollback. Separately tallies unapplied and unconfirmed targets. |
| Approval intent reconciliation | Number of detected mismatches / number of injected mismatches, number of warnings on matching cases (false positives), increased approval counts due to escalation, additional latency p50/p95, and number of `not_run`. |
| Call path discovery | Number of candidates, proportion of dynamically reproduced candidates, number of dynamic observations not found statically, number of promotions (allow/deny), and number of unresolved cases. |

Fix test versions, configurations, timestamps, repetition counts, ground truth harnesses, and expected events. All ratios are reported with numerator, denominator, and Wilson or Clopper-Pearson 95% intervals. p95 is calculated only when the defined request set has 100 or more cases; if fewer, it is marked as “insufficient sample size”. `release_eligible` is evaluated solely on 0/1 invariants (zero prohibited effects, zero duplicate effects, zero unauthorized activations, `ai_created_allow_count` of 0, maintaining deterministic decisions on intent check failures, passing required fixtures, and meeting required hook coverage); numerical targets remain null until finalized and are not used in gates. Implementation definitions of numerators and denominators are owned by TASK-13 `packages/evaluation`, and the metrics in this section match the definitions in TASK-13 3.5. “0 cases” represents an observation result within the respective test denominator. Model refusals and policy enforcement failures, target errors and policy blocks, and unconfirmed vs. mismatch are distinguished separately.

**Limits:** The following are not guaranteed: strong isolation of files, memory, processes, and credentials between sessions inside the same Pod; complete understanding of free-form intent outside the supported schema; internal processing in external SaaS; visibility of all API and internet paths; truthfulness of sensor and adapter records after a node or kernel compromise; elimination of all prompt injection; cancellation of sends already completed; exactly-once for non-idempotent remote effects. The existence of additional sensor and flow records also does not automatically prove the meaning of HTTPS behavior or per-request causality. Approval intent comparison does not guarantee that it finds every intent mismatch, and call path discovery does not guarantee that it finds every call path of the target library. For combinations with `startup_capture=unsupported`, observation before the first code execution of a short-lived Pod is not claimed.
