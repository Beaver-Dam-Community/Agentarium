**Required work startup guarantee (2026-10-12):** The [COMMON work startup contract](COMMON.md#agent-work-startup-contract) enforces trusted supervisor initialization → actual node observation/policy/collection readiness → identification/filters/durable record for that Pod → per-session dedicated worker bootstrap → independent observation of the worker exec and COMMIT of the session link → session permissions/budget → work start on that worker. Multiple sessions are kept as dedicated processes, and readiness, including worker liveness and the exact binding, is rechecked at new work/turn, resume, and model/tool control points. startup_guard_gate before the container's first program is an optional hardening and does not replace the default gate. Implementation/functional verification is planned/not_run.


**Dedicated worker adopted (2026-10-12):** The [COMMON worker contract](COMMON.md#session-dedicated-worker-contract) is the source of truth for the registration API, independent node witness, SessionProcessBinding, and readiness. [TASK-15](TASK-15-runtime-integration.md#session-dedicated-worker-implementation-required) describes the supervisor/worker IPC, required memory controls, same-UID file limits, unverified hardening such as Landlock, and the implementation/testing responsibilities. The default worker gate is core-required, while file hardening and startup_guard_gate are judged separately.

## Current status and reading order

Every Task is in the state **implementation spec written / implementation planned / functional verification not run**. This work is not a report on performed implementation or GCP deployment. Actual owners and planned implementation dates have not been assigned yet.

First read the Shared Spec's stack, decision status, ID dictionary, data structures, enums, reason codes, event_type registry, normalization, atomic state, health, and result recording. **COMMON is the source of truth (SSOT).** Per-Task APIs and schemas use the names from COMMON as is, and the schema blocks in the plan should be read only as conceptual summaries. At the top of each document is a structure diagram showing that Task's processing flow. The body specifies the configuration values, check items, APIs, DB constraints, permissions, rejection conditions, failure handling, code paths, tests, and pass criteria to implement. Values determined at deployment, such as the project ID, actual origins, and image digests, are registered in the environment lock. Technical terms are kept in the original and explained on first appearance.

Dependencies are divided into two kinds.

- **Development prerequisite:** the prerequisite work in the table below and in the plan's Task table. It is the minimal relation needed to start implementation and does not mean all runtime dependencies.
- **Integration dependency (runtime):** a relation needed for complete execution. For example, the gateway uses the TASK-07 storage API and the TASK-10 Health API, so both features must exist for it to run completely. The prerequisite table in each Spec lists the two relations in separate rows.

The following cycles are intentional. The TASK-01 Q0 harness is run first with prototype components of TASK-07, 09, and 10, and is run again once those Tasks are complete. TASK-12, 13, and 14 are runtime integration dependencies that call one another as proposal → regression test → deployment → retest. Mock-based development can proceed in parallel after the contracts are agreed, but mock success is not marked as GKE functional completion.

## Implementation groups

1. **Platform and Shared Spec:** TASK-01 to 02. Q0 runtime/sensor compatibility and the schema are fixed first. The candidate storage and promotion procedure for call path discovery (TASK-02) also starts here.
2. **Request control:** TASK-03 to 06. These build the identity, approval, standing rule, gateway, adapter, and egress/secret boundaries. Approval intent matching is split among TASK-04 (service and decision promotion), TASK-05 (model profile), and TASK-03 (approval screen warnings and confirmation records).
3. **Evidence and verification:** TASK-07 to 11. These build durable audit, target receipts, kernel observation/linkage/health, the hold model, and the timeline.
4. **Policy improvement:** TASK-12 to 14. These build issues, proposals, tests on the same `fixture_set_digest`, human approval, activation confirmation, and rollback. TASK-13 also tests the intent matching and call path discovery fixtures and the `ai_created_allow_count = 0` invariant.
5. **Integration and submission:** TASK-15 to 16. These complete the Google ADK agent and the reproducible results/installation documents.

**Implementation languages and OPA:** Deterministic enforcement services (gateway, coordinator, adapters, recording, node components) are implemented in Go, model-interaction services and test/analysis tools in Python 3.12, and the console in TypeScript/React. OPA is embedded in the gateway as a Go library. TASK-04 handles `matched_rule_ids` and the decision input snapshot, TASK-13 handles decision replay (`decision_replay`), and TASK-12 and 14 handle the permission widening check (`permission_widening`). Per-component languages and paths follow the [COMMON implementation stack](COMMON.md#implementation-stack-and-decision-status).

**Second revision summary (reflecting the implementability assessment):** The source of truth for the decisions below is COMMON, and each Spec uses the same names.

- **Service PKI:** Only the identity service (TASK-03) issues certificates, using a Certificate Authority Service CA pool. The SAN is `spiffe://agentarium.internal/ns/<namespace>/sa/<KSA>`, and the Pod label `app.kubernetes.io/name` equals the KSA name ([COMMON service PKI](COMMON.md#service-pki-and-identifiers)).
- **Policy deployment:** When the releaser (TASK-14) writes `desired_bundle`, the gateway and adapters read it every 2 seconds and load the signed bundle. Activation proceeds in the order hold → `desired_bundle` update → ack from all replicas → epoch CAS → activation probe ([COMMON policy deployment contract](COMMON.md#policy-deployment-contract)).
- **Decision basis:** A GatewayDecision has a `decision_basis` (`approval`, `standing_rule`, `service_scope`, `activation_probe`). A service session is allowed only by Rego `service.scope_allow.v1` within the range of the TASK-03 profile table, and the actor is `service:<namespace>/<KSA>`.
- **Regression relay:** The TASK-13 `regression-dispatcher` in the operations project writes requests to the `regression-requests` bucket, and the regression project runner writes results to `regression-reports`. Decision replay inputs are read from the `decision-input-exports` bucket ([COMMON regression test contract](COMMON.md#regression-test-contract)).
- **Installation values:** These are fixed in a single `deploy/gcp/environment.lock.json`, and TASK-16 owns its schema ([COMMON environment lock](COMMON.md#environment-lock)).

**Third revision summary (2026-10-12, reflecting the governance specification):** The source of truth is COMMON, and each Spec uses the same names. No new Task IDs were created, and everything is planned for implementation with verification not yet run.

- **Governance check items:** General items G-01 to G-27 and privacy items P-01 to P-15 are placed in [COMMON appendix C](COMMON.md#appendix-c-governance-checklist). They are tracking criteria, not compliance judgments, and the article numbers in the basis column have not been checked against the original texts. Items without a corresponding specification are marked "none".
- **Network policy records:** GKE Dataplane V2 network policy logging is enabled ([TASK-06 3.4](TASK-06-egress-credentials.md#34-network-policy-logging-configuration)), and when the node collector sends the `policy-action` records from the node file, the TASK-10 linker stores them as NetworkPolicyRecord. The collector lease is `netpol-collector` and is not a required lease. The delivery delay, address notation, and omission patterns of the logs are in the [common Q0 list](COMMON.md#common-q0-list).
- **Composite judgment:** Kernel connection events and network policy records are combined into a NetworkFinding that distinguishes attempted, blocked, and established ([TASK-10 3.7](TASK-10-correlation-health.md#37-network-policy-records-and-composite-decisions)). Segments are marked with `network_segment` and `boundary_crossing`, there is no `confirmed`, and a NetworkFinding does not create a hold. The timeline shows it as a workload item (TASK-11), and a judgment that identifies a workload becomes a `source = network_finding` issue (TASK-12, operator patch form only).
- **Permission widening comparison rules:** How to compare non-set values such as numeric limits, data classes, CIDRs, and patterns is defined in the per-kind table of the [COMMON permission widening check](COMMON.md#permission-widening-check-permission_widening), and [TASK-14 3.5](TASK-14-policy-release.md#35-permission-widening-check-permission_widening) implements it.
- **Regression test linkage:** Results per check item are aggregated through RegressionFixture's `governance_refs[]` and RegressionReport's `governance_summary` ([TASK-13](TASK-13-regression-harness.md)). `release_eligible` and `fixture_set_digest` do not change. The `network-finding-*` fixtures are in `measurement` scope.

**Fourth revision summary (2026-10-13, reflecting review comments on the third revision):** Review comments on the third revision were reflected. No new Task IDs were created, and everything is planned for implementation with verification not yet run.

- **Cloud Logging excluded:** Because of cost, Cloud Logging is not used as the storage and query means for audit records and network policy logs. GKE's sending of network policy logs to Cloud Logging as well is blocked with an exclusion. Entries not stored in a log bucket are not charged (official pricing documentation, [TASK-06 3.4](TASK-06-egress-credentials.md#34-network-policy-logging-configuration)). For network policy logs, the node collector reads the node file and sends it to the control plane ([TASK-06 3.4](TASK-06-egress-credentials.md#34-network-policy-logging-configuration)), and the Cloud Logging query replica of audit events was also removed (TASK-07). Because the collection path is on the node, node-level failures are experienced together with kernel events. The format and rotation limit of the node file are items to confirm.
- **Gap representation:** ObservationGap's `stage`, `reason`, and `recovery_state` are placed as the source of truth in the COMMON [enum definitions](COMMON.md#enum-definitions) and enforced with a DDL CHECK. A node collector failure within the file rotation limit is a delay and is closed as `backfilled` after recovery, and only intervals that cannot be re-read remain `unrecoverable` ([TASK-10 3.7](TASK-10-correlation-health.md#37-network-policy-records-and-composite-decisions)).
- **Risk event hold:** For the COMMON risk event workload hold, the reason `risk_event` and per-type judgment conditions were defined ([TASK-10 3.2](TASK-10-correlation-health.md#32-control-health-decision)). The judgment is made from kernel events alone, and blocked attempts and NetworkFindings do not create a hold.
- **Governance check items:** "Original text check" and "confirmation basis" columns were added to appendix C, and the wording of items that did not match the specification's actual behavior and limits was corrected. The machine-readable source of IDs (`tests/regression/governance_ids.json`, generated at implementation time) and `governance_map_digest` were defined, and check items were linked to the existing core and intent fixtures so that per-item results appear in the `candidate_final` report and the approval screen (TASK-14). The rules for citing article numbers in submission materials are in TASK-16.

**Independent gate and auxiliary features:** The start guarantee before first code execution was separated into `startup_guard_gate` (TASK-01 Q0, TASK-09 node runtime bridge, TASK-10 start coordinator, TASK-13 tests, TASK-16 install 4b). Combinations that fail Q0 are recorded as `startup_capture=unsupported`, and this result does not block installation, testing, or completion judgment of other features. AI auxiliary features (approval intent matching and call path discovery) follow the AI one-way principle, and even if they fail, the completion judgment of deterministic controls is not weakened. The contract is in [COMMON's Google technology usage design](COMMON.md#google-technology-usage-design).
